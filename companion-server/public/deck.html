It is my own board, built to obey an authenticated command and wipe itself. A kill-switch on gear I own, not a break-in, and no deauth.

05

…but the chip
betrays its own secrets.

The ESP32 ships with flash encryption off. One standard command, esptool read_flash, dumps everything.

The kill token and the WiFi password,
sitting there in plaintext.

"Authenticated" is only as strong as the microcontroller's secret storage, and by default that storage is an open book.

$ esptool read_flash → strings

  Kaffi_Frí
  bestcoffee        # WiFi password
  token
  ghoul-begone-2026 # kill token
This mirrors a real, recurring class of weakness: hardcoded secrets (OWASP IoT #1, Mirai) and extractable MCU flash. Mitigation: flash encryption + secure boot, never hardcode secrets.
05

Wiping it is the polite option.
The same weakness lets me take it over.

reflash it remotelypush my own firmware over OTA
crash it, no passwordone malformed 802.11 frame
clone itrebuild the board from its dump

Flash encryption and secure boot are off by default. So the chip will accept a new image, hand over its secrets, and fall over to a crafted packet. The device can't defend itself, its environment has to.

On my own board I use its own channel and a known secret, the tame version. In the wild this class has been fully unauthenticated (see next slide).
05

This isn't hypothetical.
It has already happened to this chip.

Remote takeover, no pairing

BrakTooth (CVE-2021-28139): arbitrary code execution on the ESP32 from radio range, no credentials. 2021.

One frame crashes it

Crafted 802.11 frames crash the ESP WiFi stack (CVE-2019-12588). Same radio our twin uses.

Radio-range DoS

SweynTooth (CVE-2020-13594/595): invalid packets crash or deadlock the ESP32 BLE stack.

Secrets glitched out

Fault injection recovers the flash-encryption keys (CVE-2019-17391). Even "protected" flash fell on old silicon.

Hardcoded secrets at scale

Mirai, 2016: default creds in ~150,000 devices took down half the internet at 1.2 Tbps.

Small chips must live in protected environments, with their defences turned on.

Full citations in docs/MCU_SECURITY.md. BrakTooth/SweynTooth are Bluetooth; cited as the same remote-compromise class, the WiFi CVEs show it on our twin's own radio.

Section 06

The Verdict

What actually defends, and where the line is.

06

What actually stops an evil twin.

Detect it

The Watcher. The deployable contribution, catches it from its fingerprint.

Harden the clients

WPA3 + Protected Management Frames, so devices refuse the clone. This is why the attack needed WPA2.

Find it and unplug it

Locate by signal, remove physically. The honest, legal response.

Protect the hardware

Flash encryption + secure boot ON, no hardcoded secrets, keep it patched and physically contained.

the honest limit

You can't remotely kill
a stranger's rogue AP.

The kill-switch works only because it's my own board, with my own token. Against a real attacker you detect and harden, you don't counter-hack. Naming that limit is part of the result.

06

Kept safe, kept mine.

  • Out-signal, never hide. No deauth, no jamming.
  • The relay carries traffic but never reads it. No one else is touched.
